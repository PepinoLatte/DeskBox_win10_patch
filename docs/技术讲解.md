# DeskBox 圆角补丁 — 技术讲解文档

> 本文面向想理解「为什么这么设计」的读者，按问题驱动的思路完整还原开发过程，包括踩过的每一个坑。配套的 `README.md` 是使用文档，本文是原理与设计文档。

---

## 1. 问题的本质

DeskBox 每个桌面盒子是一个独立顶层窗口。它的设置里有「窗口圆角」选项（`widgetCornerPreference: "Round"`），但在 Windows 10 上静默失效。

失效原因一句话：**DeskBox 调用的 `DwmSetWindowAttribute(hwnd, DWMWA_WINDOW_CORNER_PREFERENCE=33, ...)` 是 Win11 build 22000 才加入的 API**。在 Win10 的 dwmapi 里传入属性 33 直接返回 `0x80070057`（E_INVALIDARG），代码大概率没检查返回值，所以用户看到的是「设置无效」而不是报错。

第一性原理：要在 Win10 圆角化，只剩下两条路：

1. **GDI Region 裁剪**（`SetWindowRgn`）：告诉系统「这个窗口只有这个多边形区域内是可见的」。1995 年就有的古老机制，Win10 完全支持。
2. **Hook 绘制流程**：拦截 `WM_PAINT` / DirectComposition 提交，自己画圆角遮罩。复杂度爆炸，不考虑。

结论：`SetWindowRgn` 是唯一务实路线。它没有 DWM 合成器级抗锯齿（边缘 1px 锯齿），但工程代价最小。

## 2. 「无常驻进程」的约束推导

`SetWindowRgn` 设置的 region 是静态的——**窗口一旦改变尺寸，region 就不对齐了**。而 DeskBox 的小组件窗口会频繁创建/销毁/缩放（折叠胶囊 ↔ 展开面板）。所以必须有一个「东西」持续监听窗口事件并重新裁剪。

监听者放哪？三个选择：

| 方案 | 形态 | 问题 |
|------|------|------|
| 独立常驻进程 | 进程外 `SetWinEventHook` | 违背「零常驻」目标 |
| 进程内 DLL | 注入 DeskBox，DLL 内建监听 | 需要注入技术 |
| 系统机制 | WMI 事件订阅 | 延迟大、配置繁琐、需管理员 |

选 DLL 注入。DLL 的生命周期与 DeskBox 进程绑定：DeskBox 退出 → 进程消失 → DLL 随之消失。**桌面上永远不出现独立的补丁进程**——这就是「融合进主程序」的实质：不是修改主程序文件，而是让补丁逻辑寄生在主程序的进程空间里。

## 3. 版本免疫设计

「适配每一次更新」的关键：**不依赖任何会随版本变化的东西**。

| 依赖项 | 会变吗 | 处理 |
|--------|--------|------|
| DeskBox.exe 内存偏移/指令 | 每次版本可能变 | 完全不碰 |
| 窗口类名 `WinUIDesktopWin32WindowClass` | 不归 DeskBox 控制——它来自微软 WinUI3 框架（`Microsoft.UI.Xaml.dll` 注册的固定类名） | 作为主识别标识 |
| 窗口样式（无边框、无 `WS_CAPTION`） | 稳定 | 兜底校验 |
| 进程名 | 稳定 | 注入前校验 |

只要 DeskBox 不脱离 WinUI3 框架，补丁就持续有效。

## 4. 注入链的四个坑（实战记录）

启动器 → 注入 → 初始化的链路看着简单，实际有四个隐蔽的坑，全部真实踩过：

### 坑 1：路径解析的尾部反斜杠

启动器需要从「自己所在目录」推出「上级目录的 DeskBox.exe」。`PathRemoveFileSpecW` 对 `"D:\...\RoundPatch\"` **不做任何事**——因为尾部反斜杠意味着「这是个目录，没有文件名可删」。必须先 `PathRemoveBackslashW` 再 `PathRemoveFileSpecW`。

### 坑 2：导出符号缺失

DLL 的 `RoundPatch_Entry` 最初只写了 `DWORD WINAPI`（= `__stdcall`），没加 `__declspec(dllexport)`，结果导出表里根本没有它。启动器 `GetProcAddress` 拿到 `NULL`，后续二跳被静默跳过。**远程注入链最怕这种「静默跳过」**——每一步都要么成功要么大声失败。

教训：PE 导出表要用工具验证（`pefile` / `dumpbin /exports`），不能「编译过了就行」。

### 坑 3：`GetExitCodeThread` 在 x64 上截断

需要知道 DLL 注入后在目标进程的基址，第一反应是让远程线程跑 `GetModuleHandleW` 然后 `GetExitCodeThread` 拿返回值。**x64 的模块基址通常是 `0x7FF8xxxxxxxx` 这样的高地址，而线程退出码只有 32 位**——高 32 位被截断，拿到的基址是错的。

正确做法：`CreateToolhelp32Snapshot(TH32CS_SNAPMODULE, 目标PID)` + `Module32FirstW/NextW` 遍历模块列表，`MODULEENTRY32W.hModule`（即 `modBaseAddr`）是完整的 64 位地址。

### 坑 4：`WINEVENT_OUTOFCONTEXT` 的线程绑定（最隐蔽）

`SetWinEventHook` 带 `WINEVENT_OUTOFCONTEXT` 标志时，事件回调**投递到「安装 hook 的线程」的消息队列**，由该线程的消息泵分发。最初的设计是「注入后远程线程直接执行初始化」——但远程线程跑完 `RoundPatch_Entry` 就退出了，**安装在上面的 hook 随线程死亡而失效**，一个事件都收不到。

修复：`RoundPatch_Entry` 里 `CreateThread` 一个专门的监听线程，它安装 hook 后进入 `GetMessageW` 消息泵循环常驻。这个线程活着，hook 就活着；DeskBox 进程退出，它自然消亡——不违背零常驻目标。

这个坑的排查花的时间最长：hook 句柄返回非 NULL、线程在跑、消息泵在转，但事件就是不来。最后用「Python 全局 hook 对照实验」确认系统事件链正常，才把问题锁定到线程生命周期上。

## 5. 位运算乌龙：`0x14080000` 里没有 `WS_POPUP`

最初的目标窗口校验逻辑：

```c
if ((style & WS_POPUP) == 0) return FALSE;   // 要求有 WS_POPUP
```

实测小组件窗口 `style = 0x14080000`，拆解：

- `0x10000000` = `WS_VISIBLE`
- `0x04000000` = `WS_CLIPSIBLINGS`
- **没有** `0x80000000`（`WS_POPUP`）

看走眼的地方：`0x14 08 00 00` 里的「8」在第 2 字节（`0x08`），而不是最高字节的 `0x8...`。`WS_POPUP` 位是 0。这个窗口是无边框的 overlapped 窗口，不是 popup 窗口。

校验逻辑最终改成「排除法」：

```c
if ((style & WS_CAPTION) == WS_CAPTION) return FALSE;  // 有标题栏的不是小组件窗
```

只拒绝确定不是的，不要求确定是的——这让校验对 DeskBox 窗口样式的微小变化更宽容。

## 6. 验证环节的 DPI 陷阱

开发中发现「检测脚本永远报告 region 没生效，但实际圆角已经成功」。原因：检测脚本（Python）默认不是 DPI-aware 进程，在 150% 缩放的系统上，它调用 `GetWindowRect` / `GetWindowRgn` 走的是 DPI 虚拟化坐标，跨 DPI 上下文的窗口属性查询返回异常值。

而 `SetWindowRgn` 的 `ok=1`（DLL 日志）+ 截图目视确认圆角都在。结论：**DPI-aware 的环境下做 GUI 自动化验证，`SetProcessDpiAwareness` 必须显式声明**；以及——视觉验证永远比 API 推断可信。

## 7. 整体时序

```
用户双击快捷方式
    │
    ▼
DeskBoxRound.exe（启动器）
    │ CreateProcessW(CREATE_SUSPENDED)
    ▼
DeskBox.exe（主线程挂起中）
    │
    │ 启动器侧：
    ├─ VirtualAllocEx + WriteProcessMemory 写入 DLL 路径
    ├─ CreateRemoteThread(LoadLibraryW)          ← DLL 加载进目标进程
    ├─ Toolhelp 快照枚举远程模块基址               ← 避开 GetExitCodeThread 截断
    ├─ 计算远程 Entry 地址 = 远程基址 + 导出偏移
    ├─ CreateRemoteThread(RoundPatch_Entry)      ← 初始化
    │       └─ Entry 内部：LoadConfig + CreateThread(监听线程)
    │               └─ 监听线程：SetWinEventHook ×2 → ApplyAll → GetMessage 泵
    ├─ ResumeThread                              ← DeskBox 主线程开跑
    └─ 启动器退出（全程 <5 秒）
    │
    ▼
DeskBox 正常运行，监听线程随窗口事件实时裁剪圆角
DeskBox 退出 → DLL、监听线程、hook 全部随进程消亡
```

## 8. 安全性说明与杀软误报

启动器使用了 `CreateRemoteThread` + `LoadLibraryW` 注入。这是杀软重点监控的行为模式（大量恶意软件也这么干），属于本类补丁的**固有误报**——没有绕过检测的意图，也没有对抗代码。应对方式：

1. 全部源码开源，任何人都可自行编译验证
2. README 提供「自己编译」的完整命令（clang 一行命令，无需 VS）
3. 文档里给出加白路径指引

本机 Defender 实测（实时保护开启、病毒库最新）：未报毒。但不同杀软引擎行为不同，发布后建议多引擎验证。

## 9. 可以改进的方向

- **抗锯齿圆角**：把 region 裁剪换成「窗口置于 DirectComposition 视觉树 + 圆角遮罩层」可做到完美抗锯齿，但依赖 Win8.1+ 的 DComp API，且复杂度上升一个数量级
- **配置热重载**：DLL 已导出 `RoundPatch_Reload`，未来可做一个托盘小工具监听 ini 变化触发（当前需重启 DeskBox）
- **自动重注入**：DeskBox 崩溃自动重启的场景（RestartAgent.exe）目前不走启动器，需用户手动从快捷方式启动
